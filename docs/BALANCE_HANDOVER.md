# Next! 밸런스 조정 인수인계 (BALANCE_HANDOVER)

작성: 2026-09-25 · 게임 v0.9.0 · 이 문서만 읽고 밸런스 작업을 시작할 수 있게 썼다. 프로젝트 전반은 `HANDOVER.md`, 실행/구조는 `README.md`.
(공개 사본 — 관리자 패널 여는 법은 가려져 있다. 전체본은 로컬 원본 폴더에 있다.)

---
## 1. 지금 왜 밸런스 작업이 필요한가
- 물건 정리(38→31종 정의, 실제 정의 39개 중 판매 물건 정리)·도매 처분율 변경 뒤 **자연스러운 플레이어의 파산율이 16% → 약 21%** 로 올랐다(시뮬 n=100, 시드 고정). 원래 목표는 **≤ 12%**(제안값 — 사용자 확정 전이면 사용자에게 확인).
- 그 뒤에 **돈이 나가는 곳이 새로 생겼는데 아직 재측정하지 않았다**(아래 §4). 즉 현재 실제 난이도는 시뮬 수치보다 더 어렵거나(고정비) 다를 수 있다.
- 사용자 지시: **"밸런싱은 일단 대기"** 였다가 이제 **다른 세션/다른 모델에서 진행**하기로 했다. 사용자가 확정한 원칙: 기능(서신 상점·신문 구독·경비·대출 등)을 **없애지 말고 수치로 조정**한다.

## 2. 반드시 지킬 것
1. 스토리/엔딩 조건·문구·UI는 건드리지 않는다(밸런스 = 수치·확률·가격·임대료·손님 수 등 데이터 값만). 엔딩 도달 구조를 바꾸면 사용자에게 먼저 확인.
2. 게임 수치의 원본은 `js/data/config.js`(전역 경제), `js/data/shop.js`(서신 상점·달력·경비), `js/data/items.js`(가격·원가), `js/data/factions.js`(손님 요청·지불 배율), `js/data/events.js`(사건 확률), `js/data/letters.js`(대출 등). 코드(`js/systems/*`)의 공식은 바꾸지 말고 데이터로 조정한다. 코드를 바꿔야 하면 이유를 남긴다.
3. 수정 후 반드시: `node tools/data_lint.js`(수정 전후 동일), `node tools/qa_checks.js all 200`(예외 0·삼킨 오류 0·60일 초과 0·엔딩 없음 0), 저장 왕복 통과.
4. 배포: 원본에서 `python tools/deploy_web.py` → `../armsdealer-web` 에서 `git add -A && git commit && git push origin main`. 수치만 바꿔도 `js/data/config.js` 의 `version` 을 올려 우상단 표기로 구분한다(예 v0.9.1). dev.html 은 `python tools/make_dev.py` 로 재생성.
5. 로컬 서버는 `python tools/serve.py 8765`(캐시 꺼짐). 그냥 `http.server` 는 옛 JS 가 남는다.

## 4. 아직 재측정하지 않은 것 (우선 확인)
- 신문 구독 10G × 약 39일 ≈ 390G, 경비 20G/일(고용 시), 서신 상점 구매(지도·평판지·정보통·달력·간판 합 약 550G+), 창고 확장 최대 1500G — 이 고정비/투자가 초·중반 현금 흐름에 주는 영향. 특히 **초반 5일**(시작 300G → 5일째 금고)과 **26일째 마지막 대출 할부(170G) + 임대료(80G)** 가 겹치는 구간에서 파산이 몰린다(이전 측정: 파산 중앙값 27일).
- 시뮬레이터 정책이 새 기능(신문 구독·서신 상점·경비·대출)을 **사용하지 않을 수 있다**. `tools/sim_lib.js`·`sim_suite.js` 가 상점/구독 행동을 하는지 먼저 확인하고, 안 하면 (a) 구독을 기본 켬으로 가정하는 옵션을 추가하거나 (b) 사람 성향 정책에 "구매 규칙"을 넣어야 실제와 비슷해진다. 이 시뮬 한계를 결과 해석에 반드시 적을 것.
- 물건 정리 후 **시뮬 정책이 보석·마나 물약을 들이지 않아** 요청을 돌려보내며 관계가 깎이고 파산이 늘어난 측면이 있다(`design/items_cleanup.md`). 즉 21% 중 일부는 시뮬 착시다 — 사람 성향(merchant/kind/exploratory)과 함께 봐야 한다.

## 5. 측정 도구와 방법 (node 필요, 게임 파일은 건드리지 않음)
```
node tools/sim_suite.js 200 --tag=NAME [--quick] [--only=stage,stage]
```
- natural N판 + 다른 사람 성향(상인·친절·탐색 각 N/4) + 세력 집중(도적·고블린·요정·드워프·왕국·레온 각 N/5) + 줄거리 탐침(밀고자·별조각·장부·핀·궁정·천칭단·박쥐)을 병렬·시드 고정으로 돌려 **엔딩 도달률·파산율·시기별 금고**를 표로 낸다. 결과: 콘솔 + `design/qa_suite_<tag>.json`. 기준선 파일: `design/qa_suite_base.json`, `qa_suite_c40final.json` 등(가장 최근 것은 파일 시각 확인).
- `tools/sim_probe.js`(줄거리 탐침), `sim_human.js`(사람 성향 정책), `sim_dragon.js`, `sim_qa.js`, `sim_tables.js`, `content_audit.js`. 환경변수 `WS_CFG='{"rent":25,...}'` 로 config 를 덮어써 **파일을 고치지 않고** 후보 값을 시험할 수 있다(`tools/sim_lib.js`).
- 무결성: `node tools/qa_checks.js [save|scan|all] [N]`, `node tools/data_lint.js`.
- 과거 튜닝 기록·반복 방법론: `design/qa_report_3.md`(I0~ 반복 로그와 결과표), `qa_report_1.md`·`qa_report_2.md`, `design/items_cleanup.md`(물건 정리 뒤 전후 표), `design/final_qa.md`.

### 기준선 (참고)
- 3단계 QA 최종(엔딩 27종 시절, natural 500판): 파산 **10.6%**, 최다 결말 16.4%(숲이 기억하는 가게), 27/27 등장, 합집합 ≥1% 25/27, 상인형 파산 0%, 친절형 3.2%, 탐색형 21.6%, 5일째 자연 플레이어 금고 ≈ 2배 수준.
- 물건 정리 직후(n=100): natural 파산 **21.0%**(잔금 1501G) — 정리 전 16.0%(잔금 1984G). 엔딩 종류(스캔 100판) 20/27 → 17/27.
- 엔딩은 현재 **28종**(기회주의자 `opportunist` 추가, 철의 왕·촛불 여왕 조건 완화). 도달률 표를 다시 측정해야 한다.

## 6. 조정 후보(레버) — 작은 것부터
1. 임대료 단계(`rentSchedule`)와 마지막 대출 할부·26일 부근 겹침 완화 — 파산이 몰리는 시점(중앙값 27일)을 직접 겨냥.
2. 신문 구독료 10G → 낮추거나(예 5G) 신문 구독 시 정보 가치를 올리는 대신 유지. 서신 상점 가격(평판지·달력 100G, 정보통 150G) 조정.
3. `customersPerDay [4,6]` → 초반만 +1, 또는 간판 +1 효과 강화.
4. 시작 금화/시작 재고, 5일째 광석 궤짝 등 초반 완충(단, 강철의 시대가 쉬워지지 않게 — `qa_report_3.md` I3~I5).
5. 도매 원가 `costMods` ×1.25 완화(예 ×1.2) — 전 구간에 영향, 마지막 수단.
6. 대출 이율/연체율(`letters.js`)·경비 일당(`shop.js guard.wage`).
- 주의(과거 교훈): 세계 사건을 조이면 특정 엔딩(강철의 시대·자정의 대관식 등)이 30~45%를 삼킨다. 경제를 풀 때는 **어느 한 엔딩 비율이 20%를 넘지 않는지**를 같이 본다.

## 7. 합격 기준 (제안 — 사용자 확정 필요)
- natural 500판: 파산 ≤ 12%, 최다 엔딩 ≤ 20%, 엔딩 28종 중 20종 이상이 합집합 ≥1%, 예외/삼킨 오류/60일 초과/엔딩 없음 0.
- 사람 성향: 상인형 파산 ≈ 0%, 친절형 ≤ 5%, 탐색형 ≤ 25%.
- 저장 왕복 전부 동일. 튜토리얼 흐름(첫날 5명, 첫날 마감 후 신문 구독 튜토리얼)이 깨지지 않을 것.
- 결과 보고: 바꾼 값(파일·전→후), 근거 수치(전후 표), 시뮬 한계, 사용자 결정이 필요한 것을 `design/qa_report_4.md` 로 남길 것.

## 8. 함정
- Windows: 한글 출력은 `PYTHONIOENCODING=utf-8`, 파이썬 heredoc 의 이스케이프가 납작해질 수 있으니 여러 줄 파일은 파일 쓰기 도구로.
- 시뮬은 UI 를 거치지 않아 UI 안전장치(0.5초 길게 눌러 거절, 확인 단계)가 없다 — 사람과 다르다.
- `js/data/ending_art.js` 는 생성물, 밸런스와 무관. 엔딩 그림 작업이 다른 곳에서 동시에 진행 중일 수 있으니 `assets/ending`·`design/ending_art` 는 건드리지 말 것.
- 게임 원본 폴더는 git 저장소가 아니다. 수정 전 `design/`·`js/data/` 를 복사해 백업하거나 `WS_CFG` 로 시험한 뒤 확정 값만 반영한다.
